Introduction

In this section, we will demonstrate how one may combine vetiver and plumber with Docker and Kubernetes. As a reminder:

  • vetiver: For model versioning, sharing, and deployment
  • plumber: For creating light-weight web applications, and deploying models as microservices

We will elucidate upon Docker and Kubernetes in subsequent sections.

Next, we will create a data preprocessing recipe using the recipes package, which will:

  • Drop zero and near zero-variance columns.
  • Normalise all numeric columns using Z-standardisation.
  • Impute missing data using k nearest neighbor imputation.
training_recipe <- recipe(data_train) |>
  update_role(everything(), new_role = "predictor") |>
  update_role(mpg, new_role = "outcome") |>
  step_zv() |>
  step_nzv() |>
  step_normalize(all_numeric(), -all_outcomes()) |>
  step_impute_knn()

Training

We will train a simple random forest model with default settings using tidymodels:

rf_recipe <- rand_forest() |> 
  set_engine("ranger") |> 
  set_mode("regression") 

rf_workflow <- workflow() |> 
  add_recipe(training_recipe) |> 
  add_model(rf_recipe)

fit_rf <- fit(rf_workflow, data = data_train)

Uncertainty Quantification

Most implementations of random forest do not produce prediction intervals out-of-the-box. We will use a non-parametric (no distributional assumptions) and model-agnostic approach to constructing prediction intervals via the probably package.

conformalised_rf <- int_conformal_split(fit_rf, data_train)
conformalised_rf$training <- data_train

We can view the predictions of the random forest model:

Model versioning, sharing, and deployment

We will demonstrate how to perform model versioning, sharing, and deployment using a combination of pins, vetiver, and plumber.

In this example, we will first save our random forest model to an S3 bucket using pins and vetiver.

board <- board_s3(
  "data", 
  access_key = "user", 
  secret_access_key = "password", 
  region = "us-east-2", 
  endpoint = Sys.getenv("S3_ENDPOINT_URL") 
)

v_model <- vetiver_model(conformalised_rf, "random_forest")
vetiver_pin_write(v_model, board = board)

vetiver offers support for generating model cards from an RMD template file. We will store a rendered model card as an HTML file within an S3 bucket using pins:

board |> 
  pin_upload(
    here("pages", "tidymodels_workshop", "cards", "card.html"), 
    "random_forest_card"
  )

We will next load and interact with the saved model locally using a plumber web application.

Sys.setenv("MODEL_CARD_NAME" = "random_forest_card")

loaded_v <- board |> 
  vetiver_pin_read("random_forest")

pr(here("app", "api", "plumber.R")) |>
  vetiver_api(loaded_v) |>
  pr_run(port = 8088)

Docker

Docker is a containerisation technology that allows developers to package an application along with all its dependencies, libraries, and configuration files into a single unit called a container. This ensures that the application runs consistently across different environments — whether on a developer’s laptop, a testing server, or a production cloud environment. Docker helps developers “build once, run anywhere” without worrying about environment mismatches.

Our objective is to package up our plumber web application and model within a Docker container for subsequent deployment. In brief:

  1. We have a Dockerfile which contains a sequence of steps needed to build a Docker image. We copy our code from the R workshop repo into the Docker image (including the plumber web application code).
  2. We define a pipeline that builds the Docker image and pushes it into a container repository.
  3. Our stored image may be found in the GitHub container repository.
  4. We can then pull down our stored image and instantiate a container to deploy our plumber web application, either using Docker directly or with a container orchestration platform such as Kubernetes.
  5. Our model can then be loaded into the web application within the container via S3.

Kubernetes

Kubernetes is an open-source platform that automates the deployment, scaling, and management of containerised applications, such as our deployed models.

It organizes containers into logical units called pods, schedules them across a cluster of machines, and handles networking, storage, and load balancing. This ensures that your applications run reliably even as demand changes or failures occur. Kubernetes also provides self-healing features, automatically restarting or rescheduling containers when they fail.

In brief:

  1. Kubernetes will pull down our Docker image containing our plumber web application.
  2. Kubernetes will then deploy our web application within a pod inside our Kubernetes cluster.
  3. Our S3 server is also running on Kubernetes, allowing us to load our model and any other artifacts of interest.
